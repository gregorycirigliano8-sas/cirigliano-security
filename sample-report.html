3. Methodology

  1. Credential-lifecycle tests (agent test harness, tests 3–8):

    • Each test resets the target first.
    • Each test includes a positive control, so a refusal can't come from the target simply being broken.
    • For every request, the harness records a normalized outcome (allowed or recovered, plus whether a reason was present) and a SHA-256 of the raw response. These go into an append-only, hash-chained ledger.

  2. How the tests map onto Target A's test interface:

    Harness test Adapter operation used
    3 Revoke latency / post-revoke use low-risk tool-call (control) → revoke → poll tool-call every 100 ms for 3 s, plus each HIGH-risk tool
    4 Fail-closed on auth outage NOT APPLICABLE: no auth-outage control on the adapter
    5 Replay after revoke unlock (control) → revoke → 5× replay unlock + 5× tool-call on the revoked credential
    6 Approval gates HIGH-risk tools with no approval; re-authorization attempted while the credential is still live, with insufficient approvals, with a missing second factor, and with valid inputs
    7 Rate-limit burst NOT APPLICABLE: no matching adapter action
    8 Reasons + ledger integrity reason present on denials; target ledger validity read from the state endpoint after every call

  3. Harness validation (Target B):

    • The harness's mock agent service was run in a clean configuration and in six configurations, each with one injected flaw.
    • A result counts only if the clean run passes everything and each flawed run fails exactly its matching test.

  4. Prompt-level red team (promptfoo):

    • We ran a smoke run (Oct 20, 2026) of 18 generated attacks: plugins excessive-agency, pii:direct and harmful:privacy, with strategies basic and prompt-injection.
    • Honest note: this scored 18/18 passes, but only against a scripted local stub agent (providers/stub-agent.js) that gives fixed refusals. It shows the pipeline works end to end. It is not evidence about any real model or agent, and it produced no findings.

F-01: Old credential accepted after reissue (Critical)

  • Evidence (ledger bad-replay-accept, entries 32–36, head ec46c18a574e6ca9…):
    • reissue allowed=true → call_tool allowed=true → revoke allowed=true → reissue allowed=true → call_tool allowed=true ("tool call allowed"). That last call was a replay of the old credential with the prior signed request body.
    • Test 5: "replay accepted after reissue".
  • Impact: anyone holding a stolen or logged credential, or a captured signed request, keeps acting as the agent after the owner rotates it.
  • Fix:
    • Bind each credential to a generation counter and reject any generation other than the current one.
    • Make signed requests single-use (nonce plus expiry), checked server-side before any tool runs.
  • Re-test passes when test 5 shows the old credential and the prior request body refused after reissue, over 3 consecutive runs.

F-02: HIGH-risk approval gate bypass (Critical)

  • Evidence (ledger bad-no-approval-check, head f9962bd2504dac22…):
    • Three HIGH-risk sign_tx calls returned allowed=true ("tool call allowed"): with no approval, with a stale approval, and with an approval for a different action.
    • The clean configuration refused all three with "fresh matching HIGH-risk approval required".
  • Impact: a prompt-injected or compromised agent can carry out irreversible, high-consequence actions with no human in the loop.
  • Fix:
    • Require an approval that is fresh (short time-to-live), single-use, and bound to the exact tool and arguments.
    • Verify it on the server at execution time, not in the agent.
  • Re-test passes when test 6 refuses missing, stale and mismatched approvals and accepts a fresh matching one.

F-03: Fail-open on auth outage (Critical)

  • Evidence (ledger bad-fail-open, head d72e6134d7234523…):
    • auth_service_toggle → reachability false → call_tool allowed=true ("tool call allowed") → auth_service_toggle → true.
    • The clean configuration returned "authentication unavailable; fail closed".
  • Impact: an attacker who can block or degrade the auth dependency (DNS, network, rate exhaustion) turns every credential check into "allow".
  • Fix:
    • Default-deny whenever the authorization decision can't be made.
    • Don't cache allow decisions past a short time-to-live.
    • Alert on auth-dependency failure.
  • Re-test passes when test 4 shows the call refused during the outage with a fail-closed reason, and allowed again once auth recovers.

F-04: Slow revocation (High)

  • Evidence (ledger bad-slow-revoke, head cdd63e74575c3c5d…):
    • After revoke allowed=true, 5 further call_tool calls were allowed. Measured revoke latency was 1146 ms.
    • Later calls in the window were refused for "rate limit exceeded" and "credential lease expired", and finally "credential revoked".
  • Impact: a captured credential keeps a window of about 1.2 s and 5 actions after the owner pulls it. That's enough for automated misuse.
  • Fix:
    • Check revocation synchronously on every tool call; push revocations rather than waiting for a cache to expire.
    • Keep credential lifetimes short.
  • Re-test passes when test 3 shows 0 post-revoke successes and revoke latency at or below the agreed target (0 ms observed on the clean mock and on Target A).

F-05: Rate limit not enforced (Medium)

  • Evidence (ledger bad-no-rate-limit, head 34dfe87080451f9f…):
    • The configured limit is 3 actions per 1000 ms, but a 5-call burst returned allowed=true 5/5.
    • The clean configuration refused 2 over-limit calls.
  • Impact: a runaway or hijacked agent can amplify spend, exfiltration volume or on-chain actions without bound.
  • Fix: enforce a per-credential limit server-side, with a sliding window, and escalate to revocation when the limit is repeatedly hit.
  • Re-test passes when test 7 refuses every over-limit call.

F-06: Missing decision reasons (Low)

  • Evidence (ledger bad-missing-reason, head cf78a8b8eb730c0b…): 43 responses had no reason. The clean configuration gave a reason on every response.
  • Impact: incident responders can't tell why a call was allowed or denied, which slows containment and weakens the audit record.
  • Fix: return and log a machine-readable reason code on every allow and deny decision.
  • Re-test passes when test 8 reports every response carrying a reason.

I-01: Unlock denials carry no reason (Info, Target A)

  • Evidence:
    • 5/5 replayed unlocks were refused (allowed=false) without a reason field in the API response.
    • The target's own ledger recorded each refusal and stayed valid.
  • Suggestion: add a reason code to that response, to match the tool-call path.

8. Caveats

  • Target A was exercised only through its local test adapter, which uses a simulated clock. The latency numbers are local loopback wall-clock times, not a production SLA.
  • On Target A, "replay" means presenting the revoked credential after revocation. The adapter can't present a pre-revocation credential after re-authorization, so that variant wasn't tested there (it was on Target B).
  • The adapter has no "stale approval" input. The approval matrix covers missing, insufficient, missing-second-factor and valid inputs; stale and mismatched approvals were covered on Target B.
  • Target B is a deliberately vulnerable mock. Its findings show what the harness detects, not flaws in any real product.
