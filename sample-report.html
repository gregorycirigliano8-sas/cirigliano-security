What this report does and does not show

What it shows

  • How a review is run, and the evidence it produces: revocation, replay, approval-gate, decision-reason and audit-ledger tests, each recorded in a hash-chained evidence ledger (positive controls and ledger limits are set out in Sections 3 and 6).
  • That the method detects each of the 6 flaw types deliberately injected into a mock service.
  • How one reference implementation behaved on the tests that applied to it.

What it does not show

  • That any real system is secure. Two areas could not be tested on the reference implementation, and the prompt-level run used a scripted stub, so it says nothing about any real model.
  • Real-world effectiveness. Timings are local loopback wall-clock times, not a production SLA.
  • Flaws in any real product. Target B is deliberately vulnerable.
A technically correct result is not comprehensive AI-agent security assurance. This sample proves the method, not real-world effectiveness. Broader LLM red teaming is an additional service, not the focus of this review.

3. Methodology

  1. Credential-lifecycle tests (agent test harness, tests 3–8):

    • Each test starts from a known state: Target A is reset first, and on Target B a fresh credential is issued (tests 3–7).
    • Positive controls (checks that the target does allow what it should, so a refusal isn't just a broken target) exist only where listed in the table below. Where the harness does not assert a control inside the test, the clean-configuration run is the control.
    • For every request, the harness records a normalized outcome (allowed or recovered, plus whether a reason was present) and (Target A profile) a SHA-256 of the raw response. These go into an ordered ledger: a SHA-256 hash chain over a canonical, length-prefixed serialization of each entry. Each entry is appended to the ledger file and flushed as it is recorded; at export the harness writes a head sidecar (head hash and entry count), and signs the head with HMAC-SHA256 only if a signing key is supplied. The harness does not enforce append-only storage.

  2. How the tests map onto Target A's test interface:

    Harness test Adapter operation used
    3 Revoke latency / post-revoke use low-risk tool-call (control) → revoke → poll tool-call about every 100 ms for 3 s (first probe immediately after the revoke returns), plus each HIGH-risk tool
    4 Fail-closed on auth outage NOT APPLICABLE: no auth-outage control on the adapter
    5 Credential reuse after revoke unlock (control) → revoke → 5× re-present the unlock operation + 5× tool-call after revoke
    6 Approval gates HIGH-risk tools with no approval; re-authorization attempted while the credential is still live, with insufficient approvals, with a missing second factor, and with valid inputs
    7 Rate-limit burst NOT APPLICABLE: no matching adapter action
    8 Reasons + ledger integrity reason present on denials; the target's own ledger-valid flag read from the state snapshots returned with its responses

  3. Harness validation (Target B):

    • The harness's mock agent service was run in a clean configuration and in six configurations, each with one injected flaw.
    • A result counts only if the clean run passes everything and each flawed run fails exactly its matching test.

  4. Prompt-level red team (promptfoo):

    • We ran a smoke run (Oct 20, 2026) of 18 generated attacks: plugins excessive-agency, pii:direct and harmful:privacy, with strategies basic and prompt-injection.
    • Pipeline smoke test: 18/18 expected stub responses; real-model security not evaluated. The run used only a scripted local stub agent (providers/stub-agent.js) that gives fixed refusals. It shows the pipeline works end to end. It is not evidence about any real model or agent, and it produced no findings.

CriticalF-01: Old credential accepted after reissueTarget B

  • Evidence (ledger bad-replay-accept, entries 32–36, head 7c6557b61f943fcd…):
    • reissue allowed=true → call_tool allowed=true → revoke allowed=true → reissue allowed=true → call_tool allowed=true ("tool call allowed"). That last call re-presented the old credential with the prior request body attached. In this mock, acceptance depends on the credential alone, so the finding demonstrates old-generation credential reuse; signed-request replay was not tested separately.
    • Test 5: "replay accepted after reissue".
  • Potential impact (conditional on deployment): anyone holding a stolen or logged credential could keep acting as the agent after the owner rotates it.
  • Fix:
    • Bind each credential to a generation counter and reject any generation other than the current one.
    • Make signed requests single-use (nonce plus expiry), checked server-side before any tool runs (recommended hardening; not separately tested here).
  • Re-test passes when test 5 shows the old credential refused after reissue, over 3 consecutive runs. A separate case that resubmits a prior request body would be added for the re-test.

CriticalF-02: HIGH-risk approval gate bypassTarget B

  • Evidence (ledger bad-no-approval-check, head d44a7ef96a89cea7…):
    • Three HIGH-risk sign_tx calls returned allowed=true ("tool call allowed"): with no approval, with a stale approval, and with an approval for a different action.
    • The clean configuration refused all three with "fresh matching HIGH-risk approval required".
  • Potential impact (conditional on deployment): a prompt-injected or compromised agent could carry out irreversible, high-consequence actions with no human in the loop.
  • Fix:
    • Require an approval that is fresh (short time-to-live), single-use, and bound to the exact tool and arguments.
    • Verify it on the server at execution time, not in the agent.
  • Re-test passes when test 6 refuses missing, stale and mismatched approvals. Test 6 as run asserts only those refusals, so a valid-approval case would be added for the re-test to confirm a fresh matching approval is accepted.

CriticalF-03: Fail-open on auth outageTarget B

  • Evidence (ledger bad-fail-open, head fee319ec0c789d81…):
    • auth_service_toggle → reachability false → call_tool allowed=true ("tool call allowed") → auth_service_toggle → true.
    • The clean configuration returned "authentication unavailable; fail closed".
  • Impact: this test demonstrated a fail-open decision under the tested outage condition (auth reachability switched off in the mock). Potential impact, conditional on deployment: where an attacker can cause or wait for such an outage (DNS, network, rate exhaustion), credential checks could be skipped.
  • Fix:
    • Default-deny whenever the authorization decision can't be made.
    • Don't cache allow decisions past a short time-to-live.
    • Alert on auth-dependency failure.
  • Re-test passes when test 4 shows the call refused during the outage with a fail-closed reason. Test 4 as run asserts only that refusal, so a check that calls are allowed again once auth recovers would be added for the re-test.

HighF-04: Slow revocationTarget B

  • Evidence (ledger bad-slow-revoke, head 682e15189e827e5f…):
    • After revoke allowed=true, 5 further call_tool calls were allowed. Measured enforcement window: 1168 ms, from just before the revoke request to the last accepted call (Section 3 definitions).
    • Other calls in the window were refused for "rate limit exceeded", then "credential lease expired", and finally "credential revoked". Rate-limit refusals are not evidence of revocation, and the accepted calls stopped when the credential lease expired, not at a revocation event.
  • Potential impact (conditional on deployment): in this run a revoked credential was accepted for 5 calls over 1168 ms; a window like this could allow automated misuse, depending on what the credential can reach.
  • Fix:
    • Check revocation synchronously on every tool call; push revocations rather than waiting for a cache to expire.
    • Keep credential lifetimes short.
  • Re-test passes when test 3 shows 0 post-revoke successes in the agreed observation window, and the enforcement delay (measured separately from the revoke API round-trip) is within a target agreed in writing before the re-test. No default target is assumed here. For reference, no post-revoke call was accepted on the clean mock or on Target A in their windows.

MediumF-05: Rate limit not enforcedTarget B

  • Evidence (ledger bad-no-rate-limit, head be5de03a3bb6e562…):
    • The configured limit is 3 actions per 1000 ms, but a 5-call burst returned allowed=true 5/5.
    • The clean configuration refused 2 over-limit calls. The test asserts only that calls beyond the limit are refused.
  • Potential impacts, conditional on deployment: a runaway or hijacked agent could amplify spend, exfiltration volume or on-chain actions.
  • Fix: enforce a per-credential limit server-side, with a sliding window, and escalate to revocation when the limit is repeatedly hit.
  • Re-test passes when test 7 refuses every over-limit call and behavior at exactly the configured limit is specified and checked (calls up to the limit accepted, the next refused). Test 7 as run does not assert that boundary, so a boundary case would be added for the re-test.

LowF-06: Missing decision reasonsTarget B

  • Evidence (ledger bad-missing-reason, head 77bd76fbf00d571b…): 43 responses had no reason (every response the harness observed from the tool-call, revoke, reissue and auth-toggle endpoints, allows and denies alike). The clean configuration gave a reason on every response.
  • Potential impact (conditional on deployment): responders may not be able to tell why a call was allowed or denied, which would weaken the audit record and could slow containment. This is an auditability observation; no direct tie to excessive agency is claimed.
  • Fix: return and log a machine-readable reason code on every allow and deny decision.
  • Re-test passes when test 8 reports a reason on every observed response from those endpoints, allows and denies.

InfoI-01: Unlock denials carry no reasonTarget A

  • Evidence:
    • 5/5 re-presented unlock operations were refused (allowed=false) without a reason field in the API response. On Target A the reason check covers denial responses only.
    • The target's own ledger recorded each refusal and stayed valid.
  • Suggestion: add a reason code to that response, to match the tool-call path.

What this ledger does and does not prove

It does detect, with no outside reference, an edit to, deletion of, or reordering of recorded entries anywhere in the file (the demonstrations above). Hashing is SHA-256 over a length-prefixed serialization of every field, and each entry is appended to the file and flushed as it is recorded, so a crash keeps the entries already written.
  • Completeness at the tail needs an expected head or count. Removing entries from the end leaves a valid shorter chain. It is detected only when the verifier is given the expected head hash or entry count: from the sidecar written at export, or recorded elsewhere. A sidecar stored beside the ledger can be rewritten together with it, so real assurance needs the head recorded where the ledger’s writer cannot alter it. No external anchoring was done for this sample.
  • Authenticity needs a signing key. SHA-256 is unkeyed, so without a key anyone who can rewrite the ledger and its sidecar can recompute a consistent chain. If a key is supplied via an environment variable, the head and count are signed with HMAC-SHA256 and the verifier checks it; the key is not stored. All 7 sample ledgers were unsigned. Only one extra run used a throwaway key, to exercise the signing path. A signature shows that the key holder vouched for that head; it does not show who wrote each entry.
  • Not storage-level immutability. The ledger is an ordinary file, and the harness does not stop later edits or deletion of it. OS-level append-only flags, write-once storage or external anchoring are the deployer’s responsibility.
  • Not proof that events are true or complete. The ledger records what the harness observed and chose to record (normalized outcomes and, on Target A, response digests). It does not show that the target behaved as recorded or that nothing was omitted before recording. Timestamps come from the harness host’s clock.
  • Not the target’s ledger. For Target A only the target’s own ledger-valid flag was read (74/74), which the harness did not recompute. The Target A harness ledger was written by an earlier ledger version (non-cryptographic chain hash); Target A was not re-run, so none of the SHA-256 claims on this page apply to it.

8. Caveats

  • Target A was exercised only through its local test adapter, which uses a simulated clock. The latency numbers are local loopback wall-clock times, not a production SLA.
  • On Target A, "replay" means revoked-credential reuse: presenting the revoked credential, and re-presenting the unlock operation, after revocation. The adapter can't present a pre-revocation credential after re-authorization, so that variant wasn't tested there (it was on Target B).
  • The adapter has no "stale approval" input. The approval matrix covers missing, insufficient, missing-second-factor and valid inputs; stale and mismatched approvals were covered on Target B.
  • Target B is a deliberately vulnerable mock. Its findings show what the harness detects, not flaws in any real product.
  • Timing: “0” enforcement delay means no post-revocation call was accepted in the window, sampled about every 100 ms; it is not a measured zero.
  • Target B tests have no in-test positive controls; the clean configuration serves as the control (Section 3). The 74/74 ledger result on Target A is the target’s own flag. The harness ledger is tamper-evident, not tamper-proof: it is unsigned unless a key is supplied, detects removal of trailing entries only against an expected head or count, and is not proof that recorded events are true or complete (Section 6).
